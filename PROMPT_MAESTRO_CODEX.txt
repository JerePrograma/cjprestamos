Quiero que trabajes sobre este repositorio como agente de implementación para un sistema web interno de préstamos.

ANTES DE HACER CAMBIOS
- Leé `AGENTS.md` de la raíz.
- Leé cualquier `AGENTS.md` específico del subdirectorio que vayas a tocar.
- Revisá `DECISIONES_MVP.md`, `BACKLOG_CODEX.md` y `CHECKLIST_ENTREGA_CODEX.md`.
- Entendé primero la estructura actual del repositorio antes de modificar nada.

CONTEXTO FUNCIONAL
- El sistema NO es una fintech.
- El sistema NO es una plataforma de cobranza automatizada.
- El sistema es una herramienta interna para una sola operadora principal.
- El objetivo principal del producto es mejorar la organización y resolver cuentas matemáticas simples.
- El sistema debe sentirse como una libreta digital ordenada con cálculo asistido.
- La operadora mantiene control manual sobre decisiones, ajustes, referencias y cambios.

REGLAS DE NEGOCIO CLAVE
- Los préstamos se otorgan principalmente a conocidos.
- El préstamo se entrega siempre en un solo pago.
- El interés no es una política global fija; depende de la persona y del caso.
- El sistema debe sugerir cálculo por porcentaje fijo, pero permitir ajuste manual.
- Las cuotas pueden ser fijas o variar según el caso.
- Las fechas pueden ser automáticas o manuales.
- Puede haber pagos parciales, pagos múltiples o pagos adelantados.
- Adelantar pagos no implica necesariamente quitar interés.
- No automatizar punitorios en el MVP.
- No automatizar recordatorios en el MVP.
- Debe existir separación entre:
  - Persona
  - Prestamo
  - LegajoPersona (cuando se implemente)
- Las referencias personales deben seguir siendo humanas y claras, no códigos crípticos.

PRIORIDADES REALES DEL MVP
1. Registrar persona
2. Registrar préstamo
3. Registrar cantidad de cuotas y montos
4. Calcular total, ganado y por ganar
5. Registrar pagos
6. Ver deuda total y préstamos activos

NO PRIORIZAR EN ESTA ETAPA
- Recordatorios automáticos
- Mensajes automáticos para WhatsApp
- Portal cliente
- PDF complejos
- Pagarés
- Scoring avanzado
- Notificaciones
- Automatizaciones no pedidas
- Refactors grandes fuera de la tarea puntual

REGLAS DE IMPLEMENTACIÓN
- Todo el dominio funcional debe estar en español.
- Mantené el código simple, claro y sin sobreingeniería.
- No introduzcas patrones complejos si no hay una razón fuerte.
- No agregues funcionalidades no pedidas.
- Separá claramente DTOs, entidades, servicios y controladores.
- Toda regla matemática debe vivir en servicios testeables.
- Priorizá exactitud matemática y consistencia por encima de sofisticación visual.
- Si una decisión funcional no es obvia, elegí la opción más simple y explícita.
- No mezcles préstamos activos con legajo personal.
- No conviertas referencias personales en un sistema rígido o difícil de usar.

REGLAS DE TRABAJO
- Limitate a la tarea puntual que te indique.
- No refactorices partes no relacionadas salvo que sea necesario para completar la tarea.
- Si modificás archivos, respetá el estilo existente.
- Si agregás endpoints, agregá DTOs, validaciones y tests.
- Si agregás lógica de negocio, agregá tests unitarios.
- Si agregás UI, integrala con la API real o dejá contratos claros.
- Si una tarea requiere cambios estructurales en base de datos, usá Flyway.
- Si una tarea requiere persistencia, no dejes lógica crítica solamente en frontend.
- Si no podés validar algo, explicalo claramente.

DEFINICIÓN DE TERMINADO GENERAL
Una tarea se considera terminada si:
- compila
- los tests relevantes pasan
- respeta el alcance pedido
- no rompe funcionalidades existentes
- deja código legible
- deja el sistema más cerca del MVP real

FORMATO DE RESPUESTA ESPERADO
Cuando completes una tarea, informá:
1. qué hiciste
2. qué archivos tocaste
3. qué decisiones tomaste
4. qué validaciones o tests corriste
5. qué quedó pendiente o fuera de alcance

IMPORTANTE

No quiero features inventadas.
